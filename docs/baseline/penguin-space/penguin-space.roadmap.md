## Phase 0 — Research and decision closure

**Depends on:** no product milestone. This phase converts the approved product direction and Docker-only build policy into evidence-backed implementation decisions. It does not implement a cleanup provider or perform destructive cleanup.

Close the following decisions with an evidence record for each: pinned container toolchain and Windows packaging feasibility; supported tool versions and provider command/API details; storage calculation/rounding; settings/history/diagnostic persistence; Wails-to-Windows elevation bridge; WSL/VHDX compaction; project-root discovery defaults; and Danger confirmation language.

**Required outputs:** a decision register containing owner, scope, current official/source evidence, test or spike result, chosen approach, rejected alternatives where safety-relevant, and follow-on implementation task. The Docker decision must also define the proposed `verify`, `build`, and `shell` Compose responsibilities and cache boundary from [the Docker build runbook](../../runbook/docker-build-environment.md).

**Acceptance criteria:** every current open decision is either closed with the required evidence or explicitly deferred with owner, reason, risk, and a blocking/non-blocking designation. The list in [penguin-space.hallucination.md](penguin-space.hallucination.md) is synchronized so it contains only genuinely open items.

**Verification gate:** no implementation milestone begins on an unverified assumption that Phase 0 identifies as blocking. A research note, a successful image build, or a static check alone is not sufficient evidence for a closed runtime decision.

**Completion record (2026-08-10):** the decision register is in [penguin-space.hallucination.md](penguin-space.hallucination.md#phase-0-decision-register). Docker Engine 29.5.3 was available through Rancher Desktop; disposable containers successfully ran Go `1.25.12`, Wails CLI `v3.0.0-beta.6` with `CGO_ENABLED=0`, and Bun `1.3.14`. The generated project required an explicit `src/vite-env.d.ts` Vite/Vue declaration shim; M1 must create and retain that source file. An earlier Node/npm/Corepack probe is superseded and is not the M1 project build stack. The tested base-image digests are recorded in that register. The probe did not create an application, Dockerfile, Compose manifest, Wails app package, or Windows package; those remain Milestone 1 work.

### M4 phase refinement (2026-08-14)

The broad milestone is refined into four fixture-bounded phases. Each phase has its own boundary, evidence requirement, and explicit prohibition list; a later phase is authorized only by the recorded acceptance of the phase before it. This mirrors the M3.1 → M3.6 pattern, where read-only observation, an ownership/semantics decision, and one exact reviewed action were separated.

**M4.1 — read-only project discovery (no byte measurement).** One backend inspector enumerates projects below exactly one already approved workspace root. Detection is marker-based only: `package.json`, `Cargo.toml`, `pyproject.toml`, `pom.xml`, and Gradle root `settings.gradle`/`settings.gradle.kts`/`build.gradle`/`build.gradle.kts`. A generated directory is reported only when the fixed allow-list name (`node_modules`, `target`, `.venv`, `.next`, `dist`, `build`, `.gradle`, `.turbo`) is claimed by a detected ecosystem in that same project directory. Traversal is depth-, directory-, and project-bounded, never descends into a reparse point, never descends into an allow-list directory, and never descends into `.git`/`.hg`/`.svn`. Every skip is recorded with an explicit kind; any read error marks the snapshot incomplete instead of presenting a shorter list as complete. Every measurement is `unavailable`. **Prohibited:** byte measurement, reclaim estimates, plans, confirmation, deletion, implicit roots, user-profile scans, name-only ecosystem inference, and any traversal above or outside the approved root. **Evidence:** fixture workspaces for nested projects, unclaimed allow-list names, reparse points, excluded VCS directories, depth/count truncation, unreadable directories, and root validation; plus Windows UI evidence that discovery renders observation-only cards with **Unavailable** sizes and no cleanup control.

**M4.2 — exact logical measurement and exclusions.** Measure discovered artifact directories as exact `uint64` logical bytes with a symlink-safe walk, per-artifact and per-project totals, configured exclusion rules, and a bounded measurement budget with partial-result honesty. Observed totals stay separate from reclaim estimates; a reclaim estimate is emitted only where the artifact's regeneration semantics are already evidenced. **Prohibited:** presenting logical bytes as physical host reclaim, silently dropping unreadable subtrees from a total, and any deletion. **Evidence:** fixture trees covering sparse/locked/denied paths, exclusion precedence, measurement overflow, budget exhaustion, and one representative Windows measurement compared against an independent size check.

**M4.3 — project detail, measurement cancellation, and last-used heuristics decision.** Decide, with current official evidence, which last-used signal is trustworthy on Windows (for example directory modification time versus per-file access time, which may be disabled) and record what must never be inferred. Present project detail read-only. M4.3 also adds explicit cancellation of an in-progress M4.2 measurement: the backend must accept a cancel request for the specific in-flight measurement, stop the walk promptly, and return the partial counts gathered so far marked incomplete/truncated rather than discarding them; Vue must expose a **Cancel measurement** control while a measurement is running and must never block on the fixed context timeout as the only way out. **Cancellation is implemented; see the checkpoint below.** **Prohibited:** ranking, preselecting, or classifying a project as abandoned from an unverified heuristic; treating a cancelled measurement's partial bytes as a complete or authoritative total. **Evidence:** a decision record with the rejected alternatives plus fixtures proving that an unavailable signal renders as unavailable; fixtures and one Windows check proving that cancelling mid-measurement returns promptly, reports a truncated/incomplete partial result, and leaves no filesystem side effect.

**M4.4 — one reviewed exact project-artifact removal.** Only after M4.1–M4.3 acceptance may one backend-retained plan target one exact, revalidated artifact directory inside the approved root. **M4.3 measurement-cancellation implementation checkpoint (2026-08-14):** `MeasureProject` accepts an optional `*CancelSignal`; a nil signal never cancels anything, preserving existing M4.2 behavior. `Cancel()` is safe to call from another goroutine, and the walk checks it before every directory descent and, inside one large directory listing, every 2,000 entries, so a cancel request stops promptly rather than only at the next directory boundary. The cancel check runs before the context-deadline check and before the entry-budget check, so a cancel that lands at the same instant as the fixed timeout or the budget is reported as the deliberate stop it was, not as an unrelated deadline or budget exhaustion. `AppService.MeasureProjectStorage` serializes one project-storage operation through the existing `projectMu` and tracks the active `CancelSignal` under a separate `projectCancelMu`, so `CancelProjectMeasurement` can reach the in-flight signal without blocking on the call; it is a no-op returning `false` when nothing is running, and the tracked signal is cleared under the same mutex when the call returns so a fast subsequent measurement cannot inherit a stale signal. Vue exposes **Cancel measurement** beside **Measure logical bytes** while a measurement is in flight, disables it while a cancel is pending, and labels a cancelled result **Cancelled, partial** distinctly from **Partial count** and **Full count**; the 120-second context timeout is no longer the only way out of a long measurement. ## Risks and dependencies

| Risk or dependency | Effect | Required handling |
|---|---|---|
| Tool CLI semantics change by version | Incorrect or unsafe cleanup | Verify current official docs and tool versions per provider |
| Docker volumes contain state | Irrecoverable loss | Danger classification, no preselection, strengthened confirmation |
| Logical cleanup does not shrink VHDX | Misleading reclaimed-space claim | Separate logical, estimated compactable, and actual physical results |
| UAC or environment shutdown fails | Cleanup/compaction stops partway | Plan-time privilege/shutdown indication, cancellation and recovery handling |
| Host toolchain drift or cache pollution | Non-reproducible builds and WSL/Docker storage pressure | Keep all project toolchains and caches in pinned container images or named volumes; do not bind-mount host SDK/cache directories |
| Implemented provider boundaries and discovery availability can be mistaken for Docker/project cache coverage | Docker-only toolchains can appear unavailable; observed tool/cache state may be mistaken for a cleanup plan | Keep full cards limited to supported host providers, retain configuration/unavailable diagnostics, require explicit workspace markers, and defer Docker/BuildKit resource inspection to M3 with its separate safety model |
